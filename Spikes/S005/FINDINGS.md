# S-005 findings: clipboard monitoring and pasteboard privacy

## Environment

```
ProductName:    macOS
ProductVersion: 27.0.1
BuildVersion:   26A434
Xcode 27.0
Build version 27A266a
Apple Swift version 6.4 (swiftlang-6.4.0.34.1 clang-2100.3.34.1)
arm64
```

## How to run

```
swift build --package-path Spikes/S005
B=Spikes/S005/.build/debug/S005
$B watch --level count --interval 1.0 --seconds 300   # (a) change count, nothing else
$B watch --level types --interval 0.5                 # (b) NSPasteboard.types, no data
$B watch --level data  --interval 0.5                 # (c) read every type; prints sizes and timings
$B write-marker                                       # self-made item with nspasteboard.org marker types
$B write-plain                                        # self-made plain item (neutral text)
S=$(mktemp -d -t s005-); $B images "$S"               # 1, 10, 50 MB TIFFs, plain colour and noise
```

- `watch` is an AppKit app with the accessory activation policy (no Dock icon). It stops after `--seconds` and on
  Ctrl+C. At start it records the change count and does not read the item already on the pasteboard.
- Output is type identifiers, item counts, byte counts, timings and `accessBehavior`. No text, image content or
  file names are printed.
- Steps (a), (b), (c) each ran in a separate `watch` process, one after the other.

Note 1. At the start of every run, before any read, `accessBehavior` was `alwaysAllow`. The SDK header says an app
that has not yet triggered an alert reports `default`. Guess, UNCONFIRMED: the value belongs to the process that
started the spike (a terminal session), not to the spike. This is why the "no alert" rows may not hold for an app
bundle.

### Observations

- `NSPasteboard.accessBehavior` and the detection APIs (`detectPatterns`, `detectMetadata`, "without notifying the
  person") exist from macOS 15.4 in the macOS 27 SDK header `NSPasteboard.h`. The header says the general
  pasteboard asks on programmatic access by default, and that an app appears in System Settings after its first alert.
  The detection APIs were not run.
- `NSPasteboard.types` listed 7 types for the notes copy; `pasteboardItems` showed 4 per item. The extra 3 are older
  names for the same data (`NSStringPboardType`, `NeXT Rich Text Format v1.0 pasteboard type`,
  `CorePasteboardFlavorType 0x75743136`).
- Preview copies an image as `public.png` plus one 68-byte dynamic type, not as TIFF. A plain-colour 1 MB TIFF became
  a 5,794-byte PNG; random-noise images stayed large (10 MB TIFF to 9.2 MB PNG, 50 MB TIFF to 45.6 MB PNG).
- Marker type names checked: `org.nspasteboard.ConcealedType`, `org.nspasteboard.TransientType`,
  `org.nspasteboard.AutoGeneratedType`, `org.nspasteboard.source`. The names come from the nspasteboard.org
  convention as recalled; the self-made test shows that the detection code matches these strings, not that any
  password manager writes them.

### Input for ADR-003 (encrypted clipboard store; the owner decides)

| Option | Pros | Cons |
|---|---|---|
| One encrypted file per item, plus a small encrypted index | delete and expiry are file deletes; a 45 MB image does not force rewriting other items | many files; file count and sizes are visible on disk |
| One encrypted store file for the whole history | one file to protect and wipe | every change rewrites the whole file; with tens of MB per image this is slow and wears the disk |
| A database with encrypted payload columns, large payloads as separate encrypted files | search and ordering on metadata; small items stay in one file | metadata must be encrypted too or it leaks; two storage paths to keep in step |

What the spike changes: one copy can be about 46 MB, and reading it took up to 27 ms on the main thread. So the store
should not rewrite large payloads on each change, reads should leave the main thread, and a size cap per item is
a setting worth having even though no cap was needed in these runs. Marker-type checks must run before anything is
written. Suggestion (an input, not a decision): one encrypted file per item with an encrypted index, AES-GCM with a key in the
Keychain, and a configurable size cap.

## Limits

- Bare executable started from a terminal, not an app bundle. Every permission and alert result is UNCONFIRMED for a
  real app bundle: macOS may attribute pasteboard access to the terminal app (see note 1).
- Nothing tested on macOS 15. One machine, one macOS build.
- No third-party clipboard manager was running (owner answer only). Whether macOS 27 has a built-in clipboard
  history that reads the pasteboard was not checked.
- During the level (c) run the owner copied 3 small text items outside the plan (54 bytes or less). The spike read
  them and printed sizes and type names, no content.
- "No alert" rests on the owner's answers; the code printed `accessBehavior` and successful reads at each step.
- Large-image results come from Preview, which converts to PNG. Other apps may put larger or more types on the
  pasteboard.
- Reads ran on the main thread; the 143 MB resident memory after the 45 MB copies was not tracked further.
